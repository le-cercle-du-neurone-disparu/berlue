## Chemin A — RTX PRO 6000 en `europe-west4`

### Porte 1 — Quota GPU (~5 min) ⚠️ LE RISQUE PRINCIPAL

Les quotas `NvidiaRtxPro6000GpuAllocPerProjectRegion` existent sur le projet,
mais **leur valeur n'a pas pu être lue** et n'est vraisemblablement pas
attribuée : seul le L4 a servi jusqu'ici.

```bash
gcloud beta quotas info describe NvidiaRtxPro6000GpuAllocNoZonalRedundancyPerProjectRegion \
  --service=run.googleapis.com --project=$GCP_PROJECT
```

> **Si le quota est à 0 : STOP, chemin B immédiatement.** Une demande
> d'augmentation de quota GPU se compte en heures ou en jours, pas en minutes.
> Aucune démo ne tiendra dessus ce matin.

### Porte 2 — Stockage en `europe-west4` (~20 min)

L'emplacement d'un bucket est **immuable** : il faut créer et copier, pas
modifier. Passer en multi-région `EU` est le bon choix (lisible depuis
`west1` comme `west4`), mais impose un nouveau nom — les noms GCS sont
globalement uniques et ne se libèrent pas toujours à la suppression, d'où
`BUCKET_SUFFIX` dans `.env.sample`.

```bash
gcloud storage buckets create gs://${GCP_PROJECT}-berlue-rag-eu --location=EU
gcloud storage cp -r gs://${GCP_PROJECT}-berlue-rag/* gs://${GCP_PROJECT}-berlue-rag-eu/
# idem code et models
```

Copie intra-GCP, même continent : rapide, mais 337 Mo d'index FAISS à déplacer.
Penser à répercuter les noms dans `make/config.mk` / `.env`.

**Les images ne sont PAS recopiées** : l'Artifact Registry est en `europe-west1`
région simple et pèse **26 Go** — le déplacer dans la fenêtre du matin est
irréaliste. Cloud Run sait tirer une image depuis l'AR d'une autre région : on
paie un peu d'egress au premier pull de chaque révision, et c'est tout.

### Porte 3 — Firestore (~15 min) ⚠️ L'ÉTAPE IRRÉVERSIBLE

L'emplacement d'une base Firestore est **définitif**. Il faut la détruire puis
la recréer en `europe-west4`, et réimporter.

```bash
gcloud firestore databases delete --database='(default)'        # ⚠️ pas de corbeille
gcloud firestore databases create --location=europe-west4 --type=firestore-native
gcloud storage cp -r data/backups/firestore-backup-2026-09-04 gs://<bucket-west4>/
gcloud firestore import gs://<bucket-west4>/firestore-backup-2026-09-04
```

> **C'est ici qu'on ne peut plus revenir en arrière sans réimporter.** La
> sauvegarde est faite et vérifiée (les questions de la démo sont lisibles dans
> le dump), mais entre le `delete` et la fin de l'`import`, le cache n'existe
> plus. **Ne franchir cette porte que s'il reste au moins 45 min.**

L'import restaure les documents avec leurs identifiants d'origine, donc
`_predict_cache_id(question, température)` retombe sur les mêmes clés et le
cache de la démo redevient effectif.

**Gain de la parallélisation : 2,85×**, mesuré en A/B sur la même question, la même

nuit — sur le portable, le GPU était saturé par une seule requête et les modèles

s'exprimer.

Décomposition du séquentiel (28,5 s), qui explique le gain :

```
4 s   génération + extraction + 5 échantillons (7 appels GPU)
19 s  SelfCheck — 25 passages DeBERTa sur CPU          ← 67 %
6 s   RAG — 5 appels GPU en série
```

La parallélisation fond les 6 s du RAG dans les 19 s de SelfCheck, lance les
échantillons ensemble et répartit les passages NLI sur les 8 cœurs.

## Ce que la matinée a appris

**Le cold start était le principal piège.** Trois de mes mesures (6 min 07,
7 min 22, 2 min 36) étaient polluées par un rechargement de DeBERTa après
changement de révision. J'en ai tiré deux fausses conclusions successives avant
de décomposer les logs. **Toute mesure doit être le second appel.**

Les buckets `EU` ont divisé le cold start par 4 (~6 min → 1 min 31) : le
chargement des modèles est devenu local à `west4`.

**`max-instances=1` est une protection, pas une limite.** Avec plusieurs
instances autorisées, une requête concurrente peut en démarrer une froide et
payer les minutes de chargement. Une instance unique fait patienter à la place.

**8 vCPU est le plafond Cloud Run** pour un service sans GPU (`Must be equal to
one of [.08-1], 1.0, 2.0, 4.0, 6.0, 8.0`). Les 20 vCPU de `berlue-llm` viennent
d'une configuration réservée aux services GPU.

**Le nom d'image ne suit pas le nom de service** : `berlue-api-test` tourne sur
l'image `berlue-runtime:prod`, pas `berlue-api`. Supprimer `berlue-api` en
croyant garder l'utile aurait cassé le déploiement.
